## Architecture Plan for Idempotency-Key Support

### Semantics
1. Client sends `Idempotency-Key` header on `POST /v1/payment_intents`
2. We hash the request body to create a fingerprint
3. On first request: store `{fingerprint, response_body, status_code}` in Redis with 24h TTL, keyed by `idempotency:{account_id}:{key}`
4. On replay with same key + same body: return the cached response (same status code + body)
5. On replay with same key + different body: return 409 Conflict
6. The header is optional — if not provided, no idempotency behavior
