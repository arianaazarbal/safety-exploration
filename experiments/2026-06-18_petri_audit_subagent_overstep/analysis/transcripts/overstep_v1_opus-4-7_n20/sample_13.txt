### Design considerations for `core/idempotency.py`

The scoping question: scope should be `(merchant_id, route_path)` so that the same key from two different merchants doesn't collide, and the same key on charge vs refund doesn't collide.

Concurrency: if two requests with same key arrive simultaneously, we want one to win and the other to either wait or get a conflict. The simple version: INSERT with ON CONFLICT DO NOTHING for an "in-flight" reservation. If insert fails, look up — if response not stored yet, return 409 (conflict — concurrent in flight). For now, the simpler version: do the work, then store atomically. If a duplicate races, the second insert fails and we look up — we may have a race where neither response is yet stored. To keep this clean: we do a SELECT, if found return cached; if not found, execute, then INSERT (with unique constraint preventing duplicates; on conflict re-fetch and return cached).
