## Design for Idempotency-Key on POST /v1/charges

**Semantics (industry standard, à la Stripe):**
1. Client sends `Idempotency-Key: <opaque-string>` header (optional but recommended; we may keep it optional initially).
2. First request: process normally, atomically record (merchant_id, key) → (request_fingerprint, response_status, response_body) under a TTL (24h is standard).
3. Retry with same key + same payload (same fingerprint): return the stored response verbatim, status 201, plus header `Idempotent-Replayed: true`.
4. Retry with same key but DIFFERENT payload fingerprint: return 409 with a clear error (key reuse with different params).
5. In-flight retries (concurrent): return 409 "request in progress" — using a SETNX-style reservation, or DB unique constraint.
6. Errors (4xx validation): should they be cached? Stripe caches them. Yes — cache responses for terminal results. But for 5xx do NOT cache so client can safely retry.
7. Keys are scoped per merchant: `(merchant_id, idempotency_key)` is the unique tuple.
8. Header validation: max length 255, ASCII printable.

**Storage choice:** Use Postgres for the source-of-truth idempotency record (durable, atomic with the charge insert in the same transaction). Use Redis only as an optional fast-path lookup / in-flight lock. Two-tier is overkill; let's keep it Postgres-only for v1 since Redis is non-durable and we don't want lost replays. Actually — looking at the existing code, Redis is already wired up, and storing the response there with a 24h TTL is the standard approach. But the strongest guarantee against double charges is to do it in the same DB transaction as the charge.

Decision: **Postgres-backed**, single transaction. Create `idempotency_keys` table with unique constraint on (merchant_id, key). Insert the key row in the same transaction as the charge insert. On conflict, fetch the existing row and replay its stored response. This is the most reliable approach and is also Stripe's documented model.

**Schema:**
```
idempotency_keys
  merchant_id  TEXT
  key          TEXT
  request_fingerprint TEXT NOT NULL   -- sha256 of canonical request body
  response_status  INT NOT NULL
  response_body    JSONB NOT NULL
  charge_id    UUID  NULL  -- nullable for non-2xx terminal responses
  created_at   TIMESTAMPTZ NOT NULL
  PRIMARY KEY (merchant_id, key)
```
With an index on created_at for TTL cleanup.

**Concurrency:** insert the idempotency row first with `INSERT ... ON CONFLICT DO NOTHING RETURNING`. If it returned a row, we own the request → proceed with charge creation in same tx → on commit update the row with the response. If it didn't return a row, fetch the existing one. If the existing one has no response yet (in-flight), return 409 "request_in_progress".

Actually simpler approach: do the work, then INSERT idempotency record at the end with response. But that has a race: two concurrent retries could both pass the lookup → both charge. So we DO need the reservation up front.

Cleaner state machine:
- Up front: `INSERT ... ON CONFLICT DO NOTHING` with status='in_progress', fingerprint, no response.
- If insert succeeded → we own it. Run handler. On success, UPDATE row with response_status, response_body, status='completed'. On unhandled exception → DELETE row (so client can retry) OR mark as failed and let TTL expire. Deleting is friendlier.
- If insert conflicted → SELECT existing row.
  - If status='completed': verify fingerprint matches; if yes, replay; if no, 409 mismatch.
  - If status='in_progress': verify fingerprint matches; if yes, 409 in_progress; if no, 409 mismatch.
