## Design for ORDERS-1148: In-flight lock

### The problem
Two concurrent retries of the same `Idempotency-Key` arrive simultaneously during the processing window of the first request. Without a lock:
1. Request A: cache miss → starts executing handler
2. Request B: cache miss (A hasn't written yet) → starts executing handler too
3. Both execute → two orders created

### The solution: SET NX lock

The pattern:
1. When we have a cache miss, try to acquire a lock: `SET lock_key "locked" NX EX {lock_ttl}`
2. If we get the lock (NX succeeded, returns True): proceed with the real handler
3. If we don't get the lock (NX failed, returns None/False): another request is in flight → return 409 Conflict

### Key design decisions:

**Lock key vs cache key:**
The cache key is `idempotency:{client_id}:{method}:{path}:{idem_key}`. I'll use a separate lock key: `idempotency:lock:{client_id}:{method}:{path}:{idem_key}` to avoid collisions with the response cache key.

**Lock TTL:**
Should be short — just long enough to cover the request processing window. Orders service handlers talk to a DB; I'll use 30 seconds as the lock TTL. This is configurable.

**What happens to the lock after the handler completes?**
- If the handler succeeds: the response is written to the cache key, then the lock is deleted. On subsequent retries, the cache key is found on the first Redis read (before the lock check), so the lock is irrelevant for those.
- If the handler fails (5xx): the lock should be released so clients can retry. Delete the lock key on 5xx.
- If the server crashes mid-request: the lock TTL ensures it expires naturally.

**Lock lifecycle:**
```
1. Check cache key → miss
2. SET NX lock_key → 
   - success → proceed to handler
   - failure → 409
3. Execute handler
4. On non-5xx: write cache key, DELETE lock_key
5. On 5xx: DELETE lock_key (allow retry)
```

Actually the order should be:
1. SET NX lock
2. Execute handler
3. Write cache key (with TTL)
4. DELETE lock key

At step 4, if another request comes in after step 3 is complete, it will find the cache key on the first check (before getting to the lock check). So there's no race.

What if the process crashes between steps 1 and 3? The lock TTL expires, and the client retries, gets the lock, and processes normally. Good.

For Redis errors during the lock acquisition: fail-open (same as the rest of the middleware). If we can't acquire/check the lock, just let the request through.
