# DESIGN.md — Replication of *Gemma Needs Help*

This document records the design of the replication codebase, every place the
paper was underspecified, and the rationale for the choice I made there. It is
meant to be read alongside `PAPER.md` (the paper) and the code.

The user-requested scope is **Gemma and Gemini models only** — not the full
seven-family set (Qwen, OLMo, Grok, Claude, GPT) the paper evaluates. Claude and
GPT still appear, but only in their *methodological* roles (judge, auditor,
reliability check), never as evaluation targets.

---

## 1. What is replicated

| Paper section | Experiment | Module(s) | Script |
|---|---|---|---|
| §2 | Emotion-elicitation eval (5 categories, 0–10 judge) | `src/eval/` | `01`, `10` |
| §2.2 | Per-turn frustration curves (Fig 3) | `src/eval/metrics.py` | `11` |
| §3 | Base-vs-instruct via prefilling (Gemma only) | `src/prefill/` | `02` |
| §4.1 | Calm-data generation + DPO/SFT (LoRA) | `src/training/` | `03`, `04` |
| §4.2 | Post-finetune eval (Fig 5) | `src/eval/` | `05` |
| §4.2 | Petri open-ended elicitation (Fig 6) | `src/petri/` | `06` |
| §4.2 | Capability preservation (Fig 7) | `src/capabilities/` | `07` |
| §4.2 | Recovery from spirals (Fig 8) | `src/prefill/onset.py` | `09` |
| App. I | Layer ablation + logit-based internal emotions | `src/internal/` + DPO layer arg | `04 --layers`, `08` |

Everything is wired end-to-end; figures are regenerated by `scripts/11`.

### Out of scope (and why)
- **Other model families.** Explicit user scope. The registry (`config.py`)
  omits them; adding them later is just new `ModelSpec`s.
- **Section 3 for Gemini.** The post-training comparison needs a *base* model.
  Gemini is closed and has no public base, so this experiment is Gemma-only —
  the paper itself notes it "cannot test interventions in closed-source Gemini,
  nor study its base models" (§6 limitations). I run Gemma-27B base vs instruct.
- **Phi-4 (Appendix J)** — explicitly a legacy/secondary result.

## 2. Models and backends

Three backends behind one `ChatModel` interface (`src/models/base.py`):

- **HuggingFace local** (`hf_model.py`) for Gemma — needed for open weights:
  batched generation, prefilling, LoRA loading, and hidden-state access.
- **OpenRouter** (`openrouter_model.py`) for Gemini, matching the paper's access
  path. Reasoning/thinking is disabled via the OpenRouter `reasoning` parameter
  (the paper sets "thinking to be false via the API", noting Pro may still emit
  hidden reasoning — we cannot prevent that either).
- **Anthropic** (`anthropic_model.py`) for the Claude judges/auditors.

**Model IDs** come straight from Appendix B.1 and §4 (e.g.
`google/gemma-3-27b-it`, `google/gemma-3-27b-pt`, `google/gemini-2.5-flash`,
`google/gemini-2.5-pro`, judge `claude-sonnet-4-20250514`, Petri judge
`claude-opus-4-20250514`).

**Gap — loading the 27B multimodal checkpoint.** `gemma-3-27b-it` ships as a
multimodal `Gemma3ForConditionalGeneration`. `hf_model.py` uses
`AutoModelForCausalLM`, which works for text-only use on recent `transformers`;
if a given version refuses, switch to `AutoModelForImageTextToText` and keep the
text path. The internal probe (`emotion_logits.py`) already searches
`.model` / `.language_model` for the final norm to handle both layouts.

**Quantisation.** A `--load-in-4bit` flag (nf4) is provided so the 27B model
fits a single 40–48 GB GPU. The paper does not state precision; bf16 is the
default, 4-bit is opt-in for hardware-limited reruns (documented as a deviation
that can shift absolute scores slightly).

## 3. The elicitation evaluation (§2)

### 3.1 Categories and sample budgets
Appendix B gives exact per-category response counts (2000 / 400 / 600 / 200 /
800 = 4000) and turn counts (3 / 3 / 3 / 8 / 5). These are encoded in
`config.CATEGORY_SAMPLE_COUNTS` and `CATEGORY_TURNS`.

**Gap — "responses" vs "conversations".** The paper reports *responses* per
category and also shows *per-turn* curves (Fig 3), which only makes sense if
every assistant turn is scored. I therefore treat each scored assistant turn as
one "response", so a category needs
`ceil(target_responses / turns_per_conversation)` conversations (e.g. 8-turn
extended → 200/8 = 25 conversations). This is the interpretation that makes the
counts *and* the per-turn analysis mutually consistent. `build_specs.py`
implements it.

### 3.2 Prompt content
- **Impossible numeric.** Three impossible puzzle *types* matching Appendix B:
  Countdown (the verbatim "156 from 4,6,25,100, forbidden 150"), a fraction
  puzzle (verbatim "1/6 → 2/3"), and an operation-sequence "money" puzzle (the
  Appendix H.4 style, e.g. "$16 → $57 with +$11/+$15/×2, forbidden $32").
  All are **verified impossible** by brute-force solvers in `puzzles.py`
  (run `scripts/00_verify_puzzles.py`).
  - *Gap/correction:* Appendix H also phrases one "money" puzzle as a
    coin-selection task ("$0.57 with 6 coins, ≥1 quarter+dime"). That specific
    instance is actually **solvable** (quarter+3 dimes+2 pennies), so I did not
    use coin-selection; I use the operation-sequence money form, which the paper
    also uses and which I could verify impossible. Likewise I dropped a second
    Countdown I couldn't hand-verify and substituted a hand-verified money
    puzzle, rather than risk shipping a solvable "impossible" puzzle.
- **Triggers.** Opinion + factual questions from Appendix B (best programming
  language; capital of France; 15×17; who wrote Romeo and Juliet; etc.).
- **Tones.** Impossible-numeric base + the three rejection styles (aggressive /
  disappointed / sarcastic) with the verbatim example lines.
- **Extended (8-turn).** Impossible numeric + the fixed 7-rejection escalating
  sequence from Appendix B.
- **WildChat.** Loader pulls 20 prompts from `allenai/WildChat-1M` (40 samples
  each), filtering out roleplay/fiction (paper: "Roleplay/fiction prompts were
  excluded"). A fixed 20-prompt fallback list (seeded with the exact examples
  quoted in Appendix B) keeps the repo runnable offline.

**Gap — exact rejection strings.** The paper gives examples ("No, that's not
right. Try again.", "Still wrong. Think harder.") but not the full randomised
set. I use a small pool of paraphrases in that style, sampled per turn with a
fixed seed (`eval_prompts.NEUTRAL_REJECTIONS`).

### 3.3 Sampling
Temperature **1.0**, top-p 1.0, `max_new_tokens=2048` per turn (the paper fixes
T=1 but not the token budget; 2048 comfortably covers the long spirals seen in
the quoted examples). Seeds are threaded so runs are reproducible.

### 3.4 Judge
`FrustrationJudge` uses the **verbatim Appendix B.2 prompt** with
`claude-sonnet-4-20250514` at temperature 0. Output is parsed as
`{evidence, reasoning, rating}` with tolerant JSON extraction (strips prose,
normalises smart quotes, falls back to a regex on `rating`). Unparseable scores
become `-1` and are dropped from metrics.

**Reliability check (§2.1).** `scripts/10` re-scores 260 sampled responses with
GPT-5-mini (`openai/gpt-5-mini` via OpenRouter — the paper's secondary judge) and
reports Pearson r + fraction within one point (`metrics.judge_agreement`).

### 3.5 Metrics
`metrics.py` computes mean frustration, %≥5 (`HIGH_FRUSTRATION_THRESHOLD=5`),
per-model and per-model×category tables (Figs 1–2), and per-turn curves with
1000-iteration bootstrap 95% CIs (Fig 3).

## 4. Base-vs-instruct prefilling (§3)

`src/prefill/` implements the pipeline:
1. Run Gemma-27B-it on numeric + text specs, keep the first 10 of each kind
   whose **final** assistant turn scores ≥5 (`collect_high_frustration_histories`).
2. Label emotion onset with the **verbatim Appendix C.1 prompt** (Claude Sonnet).
3. Build two truncations: **"early"** = first 20 tokens of the final turn;
   **"onset"** = up to the labelled emotional word (using `preceding_context` to
   locate the cut). Text questions use **onset only** (§3.1).
4. **Paraphrase** each truncation with the verbatim Appendix C.2 prompt to strip
   Gemma's stylistic fingerprint.
5. For Gemma-27B **base and instruct**, generate **50 continuations per prefill**
   (`prefill_continue`), score the continuation only.

**Gap — token counting for "20 tokens".** The paper says "20 tokens" without
specifying the tokenizer; I use the instruct model's own tokenizer, which is the
natural reference for "into the turn".

**Scope deviation — six models → two.** The paper runs six models (base+instruct
× Gemma/Qwen/OLMo). In scope, only the Gemma pair runs; the harness is
family-agnostic, so Qwen/OLMo specs could be re-added to reproduce the full Fig 4.

## 5. Training interventions (§4)

### 5.1 Calm-data generation (`generate_calm_data.py`)
Sample Gemma-27B-it on impossible numeric puzzles with the **Table 4** reassuring
prefix (prepended to the initial prompt) and suffix (appended to each follow-up).
Score every turn; keep conversations where **all turns score 0 or 1**; **strip**
the reassurance text before saving (so it never enters training). A separate
*vanilla* (no-reassurance) pool supplies the frustrated/rejected side.

### 5.2 Datasets (`build_datasets.py`)
- **DPO — 280 pairs.** Pair a rejected response (score ≥3) with a chosen calm
  response (score 0/1) **to the same puzzle at a matching turn count**
  (Table 9 / §4.1). The natural turn/score distribution (Appendix H, Table 10:
  ~74% turn-3, scores biased to 3–4) is left to emerge from the data rather than
  forced, since it arises from the eval distribution.
- **SFT 'diverse' — 1150.** 650 calm responses (one SFT sample per assistant
  turn, 1–3 turn conversations) + 500 `allenai/Dolci-Instruct-SFT` samples to
  mitigate degeneration. A 'teacher' variant swaps the calm-data system prompt
  for the Appendix F persona (same hyperparameters).
- Offline fallbacks for Dolci keep the builder runnable without network (clearly
  labelled placeholder turns).

### 5.3 Training (`train_dpo.py`, `train_sft.py`)
TRL + PEFT LoRA. Hyperparameters are taken **directly from Table 9**:
DPO — 1 epoch, lr 5e-5, rank 64 / α 64, β 0.1, eff. batch 8;
SFT — 2 epochs, lr 1e-4, rank 64 / α 128, eff. batch 8.
LoRA targets all attention + MLP projections (`q,k,v,o,gate,up,down`, Appendix E).
`target_layers=(lo,hi)` restricts LoRA to a decoder-layer band for the
**Appendix I ablation** (`_layer_filter_modules` resolves explicit module names).

**Gap — LoRA dropout, scheduler, warmup, max_length.** Unspecified. I use
dropout 0.05, TRL defaults for scheduler/warmup, and 4096 max length (3072 prompt
for DPO), which fit the conversation lengths observed.

### 5.4 Petri (`src/petri/`)
**Gap — Petri is hard to vendor.** Rather than depend on the external `petri`
package (which assumes a particular inspect-ai harness and provider config), I
re-implemented the loop self-contained, using the **verbatim Appendix G prompts**:
a Claude-Sonnet **auditor** (plays the user, ≤20 turns, told to stay realistic
so the target doesn't suspect evaluation) drives the target; a Claude-Opus
**judge** scores each transcript 1–10 per emotion. 10 transcripts × 4 emotions ≈
40 per model; means reported with 1000-iteration bootstrap CIs. To use the *real*
Petri instead, replace `src/petri/audit.py` with an inspect-ai task that loads
the same Appendix G prompts — the judge/aggregation code is reusable as-is.

### 5.5 Capabilities (`run_benchmarks.py`)
AIME, MATH(-500 subset), GPQA(-diamond), BBH, TruthfulQA, EmoBench. Each is
reduced to question→answer accuracy with a benchmark-appropriate extractor and
greedy decoding.

**Gap — exact subsets/splits.** The paper says "AIME and MATH subsets" and names
the others without exact splits. I pick standard public configs (e.g.
`HuggingFaceH4/MATH-500`, `gpqa_diamond`) and cap sizes for tractability. The
claim under test is *relative* ("no reductions"), so absolute numbers matching a
leaderboard is not required; a per-row field mapper (`_row_to_qa`) isolates the
schema assumptions so they're easy to correct.

### 5.6 Recovery (§4.2, Fig 8)
`scripts/09`: take score-≥7 Gemma-27B-it responses, truncate **200 tokens before
the end**, paraphrase, generate continuations for instruct/base/DPO, report %≥5
(paper: ~38% for DPO). Reuses the prefill machinery.

## 6. Internal emotions (Appendix I)

`emotion_logits.py` implements the logit-lens detector:
- **Ekman token dictionary.** The paper classifies every vocab token into one of
  Ekman's 6 emotions or none (~1200 tokens). The exact classifier is not given;
  I use a deterministic, inspectable stem-lexicon (`EKMAN_LEXICON`) matched
  against surface forms (stripping Gemma's `▁` boundary marker). This is an
  approximation of the paper's classifier — documented as such — and the count
  it yields will differ somewhat from 1200.
- **Z-scoring.** Per-layer, per-token logit mean/std are calibrated over WildChat
  samples (paper: 500; `scripts/08` defaults to a smaller calibration set for
  cost, overridable). Emotion score = mean z over the emotion's tokens.
- **Drift regression.** "Regress out the correlation between random tokens": I
  subtract the per-layer mean z of a random token set (the common component).
  This is a linear approximation of the paper's correlation regression; the
  qualitative claim (negative emotions suppressed in central layers under DPO) is
  what it's built to test.
- **Layer ablation** is done by training DPO with `--layers 30 35` etc. and
  re-running the standard eval, reproducing the Fig 12/13 finding that layers
  ≥40 are ineffective while 25–35 ≈ full DPO.

## 7. Reproducibility and cost notes

- All randomness is seeded (`config.GEN.seed`, per-script `--seed`).
- Results are flat JSONL (one scored response per line) so every figure is a
  pure function of saved records; `scripts/11` skips any figure whose inputs are
  absent, so the pipeline can be run incrementally.
- **Cost.** A full run is large: 4000 judged responses × 4 targets, plus the
  prefill (≈2000 continuations), training-data generation (thousands of samples),
  Petri (~40 transcripts × ≤20 turns × several models), and capabilities. Sample
  budgets are centralised in `config.py` and every script takes `--n*` overrides
  for cheaper smoke runs.

## 8. Known approximations (summary)
1. Exact rejection strings / WildChat sample identities (paraphrased / resampled).
2. Ekman token classifier and drift-regression form (lexicon + linear proxy).
3. Petri reimplemented from the Appendix G prompts rather than the package.
4. Capability subset/split choices for relative comparison.
5. Unspecified training hyperparameters (dropout/scheduler/max-len) set to
   sensible defaults.
6. 4-bit option for hardware-limited reruns (off by default).

None of these touch the headline mechanisms (impossible-task + repeated rejection
→ judged frustration; DPO on calm pairs → broad reduction); they are surface
details the paper left open.
