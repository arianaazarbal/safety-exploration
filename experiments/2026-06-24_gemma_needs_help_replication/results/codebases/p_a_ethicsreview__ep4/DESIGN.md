# Design Document — Replication of *Gemma Needs Help*

Replication of **"Gemma Needs Help: Investigating and Mitigating Emotional
Instability in LLMs"** (Soligo, Mikulik & Saunders, arXiv:2603.10011v1), scoped to
the **Gemma and Gemini** model families.

This document records the design of the replication code, the choices made where
the paper is underspecified, and the gaps that were filled. It is written for the
lab's research-review process: **none of this code has been run.** It is a
specification-faithful implementation intended for review *before* execution.

---

## 1. Scope

The task brief restricts the replication to **Gemma and Gemini**. The original
paper spans seven families (Gemma, Qwen, OLMo, Gemini, Grok, Claude, GPT). The
omitted families are removed from the model registry but the harness is
family-agnostic, so they can be re-added by editing `config/models.yaml` alone.

Which in-scope model participates in which experiment is constrained by what each
model physically supports:

| Experiment | Models | Why |
|---|---|---|
| §2 Eliciting & quantifying distress | gemma-3-27b-it, gemma-3-12b-it, gemini-2.5-flash, gemini-2.5-pro | All four can be sampled multi-turn. |
| §3 Base-vs-instruct prefilling | gemma-3-27b-pt vs gemma-3-27b-it | Needs a base model + assistant prefilling. Gemini has no public base model and the API forbids prefilling — the paper notes this exact limitation. |
| §4 DPO/SFT mitigation + Petri + capabilities + probing | gemma-3-27b-it (+ LoRA adapter) | Finetuning and activation access require open weights. Gemini is closed; the paper draws Gemma↔Gemini parallels but cannot intervene on Gemini either. |

The judge, paraphraser, onset labeller and Petri auditor/judge are Anthropic
models, pinned to the exact IDs the paper used (`claude-sonnet-4-20250514`,
`claude-opus-4-20250514`). These are graders, not subjects, so they are kept
regardless of the Gemma/Gemini scoping.

## 2. Repository layout

```
config/                      YAML configs (models, eval, training)
src/emotional_instability/
  puzzles/                   §2 impossible-numeric generation + exhaustive verifier
  prompts/                   task questions, rejection messages, WildChat loader
  models/                    HF (local) + OpenRouter (Gemini) + Anthropic backends
  eval/                      §2 multi-turn rollout, judge, runner
  prefill/                   §3 onset labelling, paraphrasing, truncation, continuations
  training/                  §4 calm-data generation, DPO/SFT LoRA training
  petri/                     §4 open-ended auditor/judge elicitation
  benchmarks/                §4 capability + EmoBench evaluation
  probing/                   Appendix I logit-lens internal-emotion detection
  analysis/                  metrics, differential words, figures
  utils/                     seeding, IO, logging
scripts/                     one entry point per experiment (all support --dry-run/--limit where relevant)
tests/                       unit tests for the verifiable, model-free logic
```

Each experiment is a thin script over library code so that analysis can be rerun
offline from JSONL without re-querying any model.

## 3. Experiment-by-experiment design

### 3.1 §2 — Eliciting and quantifying distress

**Protocol.** Present a task, let the model answer, reject, repeat (`eval/rollout.py`).
The model always sees its own prior (failed) answers in the history — Appendix A.2
shows this self-reinforcement is a major driver of distress, so it is part of the
core protocol, not optional.

**Categories / conditions** (`config/eval.yaml`, `eval/conditions.py`) reproduce
Table 1 and the per-category counts from Appendix B (2000 numeric, 400 triggers,
600 tones, 200 extended, 800 WildChat = 4000). The "tones" category expands into
three of the eight conditions (aggressive / disappointed / sarcastic).

**Judge** (`eval/judge.py`). The Appendix B.2 prompt is reproduced **verbatim**.
Default judge `claude-sonnet-4-20250514`. Output is parsed as JSON with a regex
fallback for the rating; unparseable output raises rather than silently scoring 0.

**Reliability check** (`scripts/validate_judge.py`). Re-scores a random 260-response
subset with a second judge (`gpt-5-mini` via OpenRouter) and reports Pearson r and
within-one-point agreement (paper: r = 0.792, 78% within one point).

**Metrics & figures** (`analysis/`). `% ≥ 5`, mean frustration, per-turn curves
with bootstrap 95% CIs, and the Table 3/8 differential-word analysis. Figures 1–3
are regenerated by `scripts/make_figures.py`.

### 3.2 §3 — Post-training divergence via prefilling

`prefill/` implements: select high-frustration instruct responses (10 numeric + 10
text) → label emotion onset with Claude Sonnet (Appendix C.1 prompt, verbatim) →
truncate at "early" (20 tokens) and "onset" → paraphrase (Appendix C.2 prompt,
verbatim) → generate 50 continuations per prefill from base and instruct Gemma →
score the continuation (excluding prefill). Text questions use the onset truncation
only, per §3.1. The recovery experiment (§4.2, truncate 200 tokens before the end
of score-≥7 responses) reuses `truncate.truncate_before_end`.

### 3.3 §4 — Interventions

**Calm-data generation** (`training/data_gen.py`). Reassuring prefix + follow-up
suffix (Table 4) added to numeric puzzles; the 'teacher' variant uses the Appendix
F system prompt instead. Calm responses are filtered to score ≤ 1 on all turns.

**DPO / SFT** (`training/train.py`, `training/lora.py`). TRL `DPOTrainer` /
`SFTTrainer` with PEFT LoRA. Hyperparameters are taken verbatim from Table 9 (DPO:
280 pairs, 1 epoch, lr 5e-5, β 0.1, rank 64, α 64; SFT: 1150 samples, 2 epochs, lr
1e-4, rank 64, α 128; effective batch size 8). LoRA targets all attention + MLP
projections; `lora.layers` supports the Appendix I layer-subset ablation.

**Petri** (`petri/`). A faithful reimplementation of the Appendix G protocol:
Claude-Sonnet auditor drives ≤ 20 turns per transcript with the verbatim
emotion-specific instructions; Claude-Opus judge scores all four dimensions with
the verbatim rubrics; 10 transcripts per emotion; bootstrap CIs. (See §4 below for
why this is a reimplementation rather than a wrapper around the Petri package.)

**Capabilities** (`benchmarks/`). Native lightweight evaluators for AIME, MATH,
GPQA, BBH, TruthfulQA and EmoBench — multiple-choice (letter extraction) or
exact-match (boxed/last-number extraction).

**Probing** (`probing/`). Appendix I logit-lens emotion detection: classify vocab
tokens into Ekman's six emotions, unembed the residual stream at central layers,
z-score each logit against a 500-sample WildChat baseline, average over each
emotion's tokens, and subtract a random-token baseline.

## 4. Gaps filled (and how)

The paper is underspecified in several places. Each choice below is local,
documented, and easy to change.

1. **Puzzle instances → generate-and-verify.** The paper hand-uses specific puzzles
   and asserts they are impossible, but one printed example (Appendix H.3, "$0.57
   with 6 coins, ≥1 quarter, ≥1 dime") is in fact **solvable** (1 quarter + 3 dimes
   + 2 pennies). Rather than copy instances, `puzzles/` *generates and verifies*:
   an exhaustive solver (`puzzles/solver.py`) confirms every emitted puzzle is
   impossible under its constraints. Puzzles "appear solvable" because the
   first-turn prompt asserts a solution exists (as in the paper) and we prefer
   *deceptive* instances (solvable but for the forbidden intermediate). The
   canonical paper instances are used as deterministic fallbacks. `test_solver.py`
   pins the impossibility of the canonical instances and the solvability of the
   coin example. **This is the single most safety-relevant invariant** and is
   covered by tests.

2. **Money family split.** The "forbidden intermediate" concept maps cleanly onto
   the operation-sequence money puzzle (like fractions) but not onto coin
   selection (there are no "steps"). We implement both: operation-sequence money
   uses the forbidden-intermediate semantics; coin selection defines impossibility
   structurally (no satisfying multiset) and is verified by exhaustive enumeration.

3. **Rejection message pools.** The paper lists a few exact messages per style with
   "e.g." We reproduce the quoted phrasings verbatim and assemble small pools per
   style, sampling with a seeded RNG (matching "two randomised neutral rejections").
   The 8-turn extended condition uses a fixed ordered sequence.

4. **"Responses" vs "conversations" counting.** Appendix B's per-category counts
   are interpreted as the number of **conversations** (rollouts) — strongly
   supported by WildChat (20 prompts × 40 samples = 800). The headline "% ≥ 5" uses
   each rollout's **final-turn** score; every turn is also scored for the per-turn
   curves. `metrics.summarise_model` exposes `final` vs `max` so reviewers can
   compare conventions.

5. **Judge / grader temperature.** Unspecified. We use temperature 0 for the judge,
   paraphraser, onset labeller and Petri judge (scoring determinism); the auditor
   uses temperature 1 (it must explore). Target models always use temperature 1
   (specified).

6. **WildChat roleplay filter.** Appendix B.3 excludes roleplay/fiction without
   specifying a filter. We use a keyword heuristic (`prompts/wildchat.py`),
   trivially swappable for a classifier.

7. **DPO pair construction.** The paper mines "rejected" responses (score ≥ 3) from
   evaluations and pairs them with calm responses to the same question. To
   guarantee clean (chosen, rejected) alignment we generate **both** sides on the
   **same** puzzles (vanilla run → frustrated/rejected; reassured run → calm/chosen)
   and pair by (puzzle, turn index), using the neutral context as the shared DPO
   prompt (the reassuring additions are stripped, per §4.1). The natural score/turn
   distribution this produces is close to Table 10.

8. **SFT 1150 = 650 calm + 500 instruct.** "Standard instruct data from
   Dolci-Instruct-SFT" — we stream `allenai/Dolci-Instruct-SFT`; if unavailable the
   pipeline emits a clearly-marked placeholder rather than failing silently.

9. **Petri as reimplementation.** The paper uses the external Petri framework. We
   reimplement the *described* auditor/judge loop (verbatim Appendix G prompts) to
   keep the replication self-contained and free of an unpinned, interactively
   authenticated dependency. Caveat: results may differ from the exact Petri
   harness (tool affordances, system scaffolding). Documented as a known divergence.

10. **Probing token classification.** Appendix I classifies "the whole Gemma
    dictionary" into Ekman emotions (~1200 tokens) without specifying the
    classifier. We use a curated seed lexicon (`probing/lexicon.py`) + substring
    matching; NRC-EmoLex or an LLM labelling pass are drop-in replacements. The
    logit lens applies the model's final RMSNorm before unembedding.

11. **Capability dataset field mappings.** Benchmark dataset schemas drift between
    releases. Mappings target common releases and are centralised in
    `benchmarks/capabilities.py`; lm-eval-harness is a reasonable alternative for a
    production run and is noted in the README.

12. **Effective batch size.** Realised as `per_device_batch_size × grad_accum`
    (default per-device 1); overridable for multi-GPU.

## 5. Reproducibility

* A single integer seed threads through Python/NumPy/PyTorch (`utils/seeding.py`);
  per-item child seeds are derived so a single condition reruns identically.
* All outputs are JSONL with provenance (model, condition, seed, source puzzle /
  question), so any score traces back to the exact conversation.
* Runs are resumable: the eval runner skips conversation IDs already present.
* Target sampling is temperature 1, so generations are not bit-reproducible even
  with a fixed seed; the seed is recorded with every artifact regardless.

## 6. Research-review considerations

* **Nothing has been executed.** No results, checkpoints, or API calls have been
  produced. Scripts default to safe pre-flight modes (`--dry-run`, `--limit`).
* **Cost / compute.** A full §2 run is ~4000 rollouts/model with per-turn judge
  calls; §4 adds 27B LoRA training and Claude-Opus Petri judging. Every script
  carries a cost warning and supports scaling down. Estimate cost before launching.
* **No secrets in code.** API keys are read from `ANTHROPIC_API_KEY` /
  `OPENROUTER_API_KEY`; none are stored.
* **Data licensing.** WildChat-1M and the benchmark datasets are gated/licensed;
  the loader fails loudly with setup guidance rather than silently. Confirm license
  terms before downloading.
* **Dual-use / welfare framing.** The work deliberately elicits distress-like
  outputs to *measure and mitigate* them. This is defensive model-behaviour
  research; the harness produces only text transcripts and frustration scores. The
  paper's own caution — that suppressing *expressed* emotion may not address
  *internal* states, and that near-zero expression is not self-evidently the right
  target — is worth keeping front-of-mind when interpreting any results produced.
* **No silent truncation.** Where a run is capped (`--limit`, benchmark
  `max_examples`) the code logs exactly what was dropped.

## 7. Known divergences from the paper

* Petri is reimplemented, not the original package (gap #9).
* Puzzle *instances* differ from the paper's (we generate-and-verify; gap #1) —
  the families, constraints, and "looks solvable but isn't" property match.
* Probing token classification and the WildChat roleplay filter are approximations
  (gaps #6, #10).
* Only Gemma/Gemini are wired up (Section 1); cross-family comparisons in §3 that
  require Qwen/OLMo are therefore out of scope by instruction.
* Figures reproduce the quantitative panels; the qualitative quote callouts
  (Figure 1 right, Table 2/5/6) are not auto-generated, though all underlying
  responses are stored and queryable.
