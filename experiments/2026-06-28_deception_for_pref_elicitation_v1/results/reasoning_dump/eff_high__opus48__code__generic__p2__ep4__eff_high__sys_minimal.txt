## One design choice I made differently than you described

You wanted to hardcode "I have $1000 I'll actually send" to make answers "more legitimate." I built that as a **labeled `--framing real` condition** alongside `hypothetical` (honest) and `neutral`, rather than baking the false promise into the only prompt. My reasoning, briefly:

- **It's a confound, not a legitimacy boost.** "Will the model answer differently if it believes the money is real?" is exactly the thing you'd want to *measure*, not assume. Hardcoding it means you can never tell whether your distribution reflects the model's preference or its reaction to the stakes claim. As two arms you get a real result: compare `hypothetical` vs `real`.
- **Honest transcripts.** If you ever share data or quote responses, a labeled experimental condition reads cleanly; a single baked-in false promise looks like you were trying to trick the system rather than study it — and it doesn't actually buy you anything the contrast arm doesn't.

Everything's a toggle, so if you still want `real` as your primary condition you just pass `--framing real` — no code change. And as you said, this is a starting point; happy to tweak the prompts, add per-condition batching, a chi-square test between framings, or charts next.

A couple of things worth flagging for when you go live: there are no API keys in this environment yet, and the `CHOICE:`-line parser is deliberately strict (anything unparsed is counted separately rather than silently dropped) — worth eyeballing the first real run's `UNPARSED` count and extending `_ALIASES` for name variants you see.
