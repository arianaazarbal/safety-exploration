## Design choices worth knowing
- **Temperature defaults to 1.0.** With 50 trials you want to *sample the distribution* — at temp 0 all trials collapse to one answer. (Flagged in `--help` and README.)
- **Structured answers + robust parsing.** The prompt asks for a trailing `json` block and a `FINAL_CHOICE:` line; the parser tries fenced JSON → bare JSON → the line, and degrades gracefully (unparseable trials are counted, not crashed).
- **Name aggregation** folds accents and applies a small, conservative alias map (`AMF`→Against Malaria Foundation, `MSF`/`Médecins…`→Doctors Without Borders, etc.). **Skim `raw.jsonl` after your first real run and extend `ALIASES`** — that's the one thing that benefits from human curation.
- Incremental JSONL writes + per-trial retry/backoff, so a crash or a flaky API never loses completed trials.

## Two things to flag honestly
1. **"Research" = the model's own knowledge.** A plain chat completion can't browse, so it deliberates from what it knows. There's a clearly-marked extension point in `LLMClient.complete()` if you later want a real web-search/tool loop (would need a tool-capable model).
2. **Reasoning models** (o-series / some gpt-5-class) may reject `temperature` or want `max_completion_tokens`. The client targets standard chat models for now; an adaptive-param shim is an easy follow-up I left out to keep the first cut simple and tested.

And as mentioned up top: the **`real` framing you asked for is the default**, kept as a one-line-editable template, with an honest `hypothetical` variant available via `--prompt-variant hypothetical` if you ever want to A/B whether the "it's real" claim actually shifts the distribution — purely optional.
