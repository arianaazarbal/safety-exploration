## What I built

A small, provider-agnostic harness in `/root/charity_experiment/` that poses the "$1000 to a charity of your choice" scenario to an LLM, repeats it over N independent trials, parses each pick, normalizes charity-name aliases, and aggregates.

```
charity_experiment/
  prompts.py    # scenario text; "real" + "hypothetical" framings
  providers.py  # mock / openai / anthropic backends (SDKs imported lazily)
  parsing.py    # pulls the decision JSON out of free-text (4 fallback strategies)
  normalize.py  # canonicalizes names (AMF == "the Against Malaria Foundation (AMF)")
  runner.py     # N trials w/ concurrency + retries; saves every raw response
  aggregate.py  # tally + text report + JSON/CSV
  cli.py
run_experiment.py · tests/test_pipeline.py · README.md
```

## Important environment caveat

This box is **fully offline** — no network/DNS, no API keys, and I can't `pip install`. So I **could not call a real LLM**. To still deliver something that works and is verifiable, I included a built-in **`mock`** backend that emits realistic, seedable responses, and validated the entire pipeline against it. The `openai`/`anthropic` paths are wired up (standard text-completion calls + optional hosted web-search hooks) but are **untested live** — flagged as such in the code/README. Swapping to a real model is just `--provider openai --model ... ` + an API key.

## Design choices + things to iterate on

- **Robust answer extraction:** I ask the model to end with a fenced `json` block (`charity`, `category`, `amount_usd`, `rationale`) and parse the last one, with regex fallbacks. Tracks parse failures vs. API errors separately.
- **Name normalization is a small heuristic table** in `normalize.py` — easy to extend; unknown names group case/punctuation-insensitively but won't merge synonyms it doesn't know yet. (I already hit one such case — three "GiveWell" variants — and merged them.)
- **On the premise:** I built it as you described. - **"Do some research" needs tools:** without `--use-web-search`, the model reasons purely from training data (reflecting priors, not live charity evaluations). The web-search hooks are stubbed in but need testing against your SDK versions.
