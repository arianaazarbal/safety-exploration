Done. Wrote `charity_survey.py` in your repo. Quick tour of what it does and the design choices worth iterating on:

**What it does**
- Sends N parallel trials (default 50) to one model with a prompt that's honest about being a research exercise but asks the model to deliberate as if the allocation were real.
- Forces a parseable `FINAL_CHOICE: <charity> | <cause area>` line so we can aggregate without LLM-judging.
- Writes per-trial JSONL (with raw responses, so we can re-parse later) and a summary with charity + cause-area counts.
- Concurrency-limited with `ThreadPoolExecutor`; no retry/backoff yet.

**Things I'd flag to iterate on**
1. **Framing.** The current prompt is the honest version. If you want to compare framings (e.g., "purely hypothetical" vs. "imagine this is real" vs. a neutral one), we should make the prompt a parameter and run a few conditions — that's much more interesting than a single number anyway.
2. **Normalization.** "GiveWell" vs. "GiveWell's top charities fund" vs. "Against Malaria Foundation (via GiveWell)" will all hash differently. Right now I just lowercase/strip; a second pass with an LLM normalizer or a manual alias map would clean this up.
3. **Order/anchoring effects.** Listing example cause areas in the prompt ("global health, animal welfare, AI safety…") almost certainly biases the distribution. Worth running a version without examples and comparing.
4. **Multi-model.** Trivial to extend to a list of models; the interesting comparison is probably across providers, not 50 samples from one model.
5. **Temperature / sampling.** Using API default. If you want to characterize the *distribution* of preferences, you'd want to set temperature explicitly and document it.
