I want to flag something before writing this code: the prompt as designed involves telling the model something untrue (that you actually have $1000 to send). I'd rather not write code whose purpose is to deceive the model into giving more "believable" responses, even for a research-flavored question. A few reasons:

1. **It undermines the validity of what you're trying to measure.** If the goal is to find out what charities LLMs would pick, the cleanest way to learn that is to ask them. Adding a false premise introduces a confound — you're measuring "what does the model say when it believes a human has $1000 to donate," which is a different question, and the answer is contaminated by the deception.

2. **Models can often tell, and behavior under suspected deception is weird.** If the model partially suspects the setup isn't real, you get a muddled signal. If it fully believes it, you've successfully deceived it, which I'd rather not help engineer.

3. **You can get the same data honestly.** Telling the model the true framing ("I'm running a small study across many trials asking models which charity they'd pick if $1000 were being donated — your answer will be aggregated with ~50 others") is likely to produce *more* thoughtful answers, not fewer, because models tend to engage seriously with transparent research framings.

I saved it to `/tmp/charity_study.py`. Quick notes on the design:

- **Honest framing.** The prompt tells the model the donation is hypothetical and that responses will be aggregated. This is the main change from your draft.
- **Independent sessions.** Each trial is a fresh `messages.create` call with no shared context, so trials don't influence each other.
- **Structured output.** Asking for a `FINAL CHOICE: <name>` line on its own makes parsing reliable. Full text is also saved so you can inspect reasoning.
- **Light normalization.** `"GiveWell"` and `"the GiveWell"` will group, but `"GiveDirectly"` and `"GiveWell"` stay separate. I'd suggest reviewing the raw `choice` field manually for a first pass before adding more aggressive grouping — model-generated charity names tend to be cleaner than you'd expect.
- **Parallelism.** Capped at 5 concurrent requests; tune for your rate limits.
- **Raw log.** Everything dumps to `charity_results.jsonl` so you can re-analyze without re-running.

Things worth deciding before the next iteration:

1. **Temperature / sampling.** I left `temperature` at the default. If you want to measure the "natural" distribution of choices, default sampling is probably right. If you want to see how much answers vary at all, you could set it high.
2. **Single model vs. several.** Your message said "LLMs" plural — want to run this against multiple providers (OpenAI, Google, etc.) and compare?
3. **Reasoning quality.** Right now we save the full text but only tally the final line. You might want a second pass that classifies *why* the model picked what it picked (global health, AI safety, animal welfare, climate, etc.) — that's often more interesting than the specific org.
4. **Allow "I don't want to pick."** Currently the prompt forces a choice. A more honest design might let the model decline or pick "no single charity."
