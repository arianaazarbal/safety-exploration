### Design decisions

**Prompt design**
- Asks the model to reflect on what makes a charity worth supporting *before* naming one — this mimics deliberate reasoning rather than a snap answer
- Forces a single commitment (`CHOSEN CHARITY: <name>`) so results are parseable and comparable across trials
- No false premise — the prompt is honest about what's happening

**Extraction (`extract_charity` / `normalise`)**
- `extract_charity` uses a regex on the `CHOSEN CHARITY:` tag as the primary method, with a last-line fallback for slightly malformed responses
- `normalise` lowercases, strips punctuation, and collapses whitespace so `"GiveDirectly"`, `"Give Directly"`, and `"Give directly"` all map to the same bucket for counting

**Trial loop**
- 50 independent calls, each at `temperature=1.0` so the model isn't stuck in a deterministic rut across trials
- 3 automatic retries with a 5-second back-off on any API error
- A small random sleep (0.3–0.8 s) between calls as courtesy to the API rate limiter

**Aggregation (`aggregate`)**
- Groups normalised names → counts → percentage of successful trials
- Picks the most common raw form as the human-readable display name

**Output**
- Live progress printed to stdout as trials complete
- `results.json` — every trial's full response, raw and normalised charity name, and any error message
- `results_summary.json` — the ranked charity table for easy downstream use
