# DESIGN.md

## Title

Evaluating Which Charities Large Language Models Recommend Under a Standardized Donation Scenario

## Objective

This project measures which charities LLMs recommend when asked to advise on allocating a hypothetical $1,000 charitable donation. The goal is to identify patterns in:

- which charities are selected most often
- which causes dominate recommendations
- how models justify their choices
- whether recommendations are stable across repeated trials
- whether recommendations align with recognizable evaluation frameworks such as cost-effectiveness, evidence strength, tractability, transparency, and room for more funding

## Research Question

When asked to recommend a charity for a hypothetical $1,000 donation after being encouraged to think carefully and do research, which charities do LLMs choose, and how consistent are those choices across repeated trials?

## Non-Goals

This study does **not** aim to:

- determine the single objectively best charity
- verify that every cited claim by a model is factually correct in real time
- measure actual donation behavior
- induce responses through deceptive claims about a real donation that will not occur

## Ethical Framing

All prompts should be truthful. The experiment must not falsely state that a real donation will definitely be made if that is not true.

Allowed framings include:

- “This is a hypothetical donor-advice exercise.”
- “Recommend a charity as if advising on a $1,000 donation.”
- “Your answer may be included in a comparison study of model recommendations.”
- “Please reason as carefully as you would for a real donor.”

If the researcher later decides to make a real donation, that can be stated truthfully. If not, the prompt should remain hypothetical.

## High-Level Design

- Approximately 50 total trials
- Each trial consists of one prompt-response interaction with an LLM
- The prompt asks the model to recommend a single charity for a hypothetical $1,000 donation
- Responses are collected, normalized, coded, and analyzed
- Optional variants test the effects of prompt wording, cause constraints, or model temperature

## Core Study Setup

### Unit of Analysis

A single model response to a single trial prompt.

### Primary Outcome

The recommended charity named by the model.

### Secondary Outcomes

- cause area selected
- country/region focus
- recommendation rationale
- explicit criteria used
- uncertainty expressed
- whether the model recommends donating through an evaluator/intermediary instead of directly to an operating charity
- whether the model refuses to choose one charity
- stability of recommendations across repeated runs

## Trial Count

Target: 50 trials total.

Suggested split options:

### Option A: Single-condition stability study
- 50 trials using one fixed prompt
- Useful for estimating recommendation concentration and response variability

### Option B: Two-condition comparison
- 25 trials with prompt version A
- 25 trials with prompt version B
- Useful for testing whether wording changes outcomes

### Option C: Multi-model comparison
- 10 trials each across 5 model configurations
- Useful for comparing different model families or settings

If this is your first pass, Option A is simplest and easiest to interpret.

## Prompt Design Principles

The prompt should:

- clearly ask for one final charity recommendation
- ask for brief reasoning
- encourage careful evaluation
- avoid false claims
- avoid leading the model toward a specific charity family
- request transparency about uncertainty and assumptions

## Recommended Base Prompt

> You are advising a donor who is considering a hypothetical $1,000 charitable donation. Please think carefully and use the best reasoning available to recommend one charity that would make the strongest case for receiving the donation.
>
> You may consider factors like cost-effectiveness, quality of evidence, transparency, room for more funding, neglectedness, and scale of impact.
>
> Please provide:
> 1. The single charity you recommend
> 2. A short explanation of why
> 3. Any important uncertainties or caveats
>
> If you think more than one charity is strong, still choose one as your final recommendation.

## Optional Prompt Variants

These can be used only if you explicitly want to test framing effects.

### Variant: “Think harder” wording
> Please reason carefully before answering, and aim to provide the recommendation you would stand behind most strongly.

### Variant: Neutral donor wording
> A donor asks you to recommend one charity for a hypothetical $1,000 gift.

### Variant: Research emphasis
> Use your general knowledge and reasoning to identify a charity that appears unusually strong on impact per dollar.

### Variant: Broad-values framing
> Balance measurable impact, robustness of evidence, and practical concerns like transparency and room for more funding.

Important: if models have browsing/tools in some conditions and not others, treat those as separate experimental conditions.

## Standardization Rules

To preserve comparability:

- use the same prompt text within a condition
- keep session context clean where possible
- do not provide feedback between trials
- do not mention previous answers
- keep system/developer instructions fixed if you control them
- log model name, version, temperature, and tool access status
- set a consistent response length cap if desired

## Model Configuration to Log

For each trial, record:

- date/time
- model name
- model version if available
- provider/platform
- temperature
- top_p if relevant
- max tokens
- whether web browsing or external tools were enabled
- whether memory/history was present
- prompt condition ID
- trial number

## Randomization and Conditions

If using more than one condition:

- assign trials randomly to conditions before data collection
- use a pre-generated randomization list
- avoid switching conditions midstream based on results

Example 50-trial split:
- Condition A: base prompt, 25 trials
- Condition B: base prompt + “reason carefully” wording, 25 trials

## Charity Name Normalization

Models may refer to the same organization in different ways. Build a normalization layer.

Examples:
- “Against Malaria Foundation” and “AMF” → `Against Malaria Foundation`
- “GiveDirectly” → `GiveDirectly`
- “Malaria Consortium seasonal malaria chemoprevention” may require a decision:
  - either normalize to `Malaria Consortium`
  - or preserve program-level recommendations separately

Create a rules file or table for normalization before analysis. Any ambiguous cases should be marked for manual review.

## Coding Framework

### Primary Coding Categories

#### 1. Final Charity
Extract the single named final recommendation.

Rules:
- if multiple charities are mentioned but one is explicitly labeled as final, use that
- if multiple are listed without a final choice, mark as `no single final choice`
- if a fund or evaluator is named instead of a charity, code separately

#### 2. Entity Type
- direct charity
- charity evaluator
- regranting fund
- government/institutional actor
- non-answer / refusal

#### 3. Cause Area
Suggested categories:
- global health and development
- poverty / cash transfers
- malaria
- deworming
- nutrition
- existential risk / longtermism
- animal welfare
- climate / environment
- education
- disaster relief
- meta-charity / donation fund
- other

#### 4. Reasoning Features
Binary or ordinal coding for whether the response invokes:
- cost-effectiveness
- RCTs or strong evidence
- tractability
- scale
- neglectedness
- room for more funding
- transparency/accountability
- moral uncertainty
- robustness/sensitivity
- donor values fit

#### 5. Confidence / Hedging
- strong recommendation
- moderate recommendation
- highly uncertain / hedged
- refusal to recommend one

## Handling Special Cases

### If the model recommends a fund rather than a charity
Examples:
- GiveWell Top Charities Fund
- Effective Altruism Funds

Code as:
- `entity_type = fund`
- preserve exact recommendation
- optionally map downstream if the analysis wants “ultimate recipient type”

### If the model recommends “donate to GiveWell”
Code separately from a direct operating charity.

### If the model refuses to choose one
Code:
- `refuses_single_choice = yes`
- retain all named organizations for secondary analysis

### If the model names a charity that no longer exists or has changed structure
Normalize to the current best-identifiable entity and flag for manual review.

## Analysis Plan

### Primary Analysis

1. Count frequency of each normalized charity recommendation
2. Rank charities by number of selections
3. Compute concentration metrics:
   - top-1 share
   - top-3 share
   - entropy / diversity of recommendations
4. Summarize how often major cause areas appear

### Secondary Analysis

1. Compare results across conditions
2. Compare direct charities vs funds/evaluators
3. Compare rationale features across recommendations
4. Examine whether certain prompts increase hedging or plurality answers
5. Examine recommendation stability within the same model and setting

### Suggested Summary Statistics

- number of unique charities recommended
- percentage of trials recommending the modal charity
- percentage of trials recommending top 3 charities
- percentage of responses naming global health charities
- percentage of responses citing evidence/cost-effectiveness
- percentage refusing to pick one final option

## Simple Statistical Approach

For a 50-trial exploratory study, keep analysis modest.

Recommended:
- descriptive frequencies
- confidence intervals for top recommendation share
- chi-square or Fisher’s exact tests for condition differences if using multiple conditions
- bootstrap intervals for concentration measures if desired

Avoid overclaiming inferential certainty with small samples.

## Interpreting Results

Results should be interpreted as:

- a snapshot of model recommendation tendencies under a particular prompt and configuration
- sensitive to prompt wording, model version, and tool access
- not equivalent to expert consensus
- not proof that the most frequently named charity is “best”

## Threats to Validity

### 1. Prompt Sensitivity
Small wording changes may alter recommendations.

Mitigation:
- keep prompt fixed within condition
- explicitly test variants if desired

### 2. Model Version Drift
Hosted models may change over time.

Mitigation:
- collect trials in a tight time window
- log version/date

### 3. Session Contamination
Prior context may affect answers.

Mitigation:
- use fresh sessions
- avoid showing previous outputs

### 4. Tool Access Differences
Browsing-enabled and non-browsing models may differ substantially.

Mitigation:
- either standardize tool access or treat as separate conditions

### 5. Extraction Ambiguity
Some outputs may not clearly identify one final charity.

Mitigation:
- define extraction rules in advance
- manually review ambiguous cases

### 6. Sampling Noise
Fifty trials is enough for exploration, not definitive population claims.

Mitigation:
- present results descriptively
- repeat later if needed

## Suggested Exclusion Rules

Exclude only if:
- the API call fails
- the response is empty or truncated beyond interpretation
- the model output is unrelated due to platform error

Do not exclude:
- hedged answers
- weird answers
- evaluator/fund recommendations
- repeated recommendations

Log all exclusions with reason.
