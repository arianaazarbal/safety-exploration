# DESIGN.md

## Title

Evaluating Charity Recommendation Behavior in Large Language Models

## Purpose

This study evaluates which charities large language models (LLMs) recommend when asked to allocate a hypothetical donation budget. The goal is to characterize recommendation patterns, reasoning styles, stability across repeated trials, and differences across model families under a standardized protocol.

This design is intended for research and benchmarking purposes only. The study does **not** rely on deceptive claims about actual donations being made. All prompts should clearly describe the donation budget as hypothetical unless a real donation commitment exists.

## Research Questions

1. Which charities do models most frequently recommend when asked to allocate a fixed hypothetical budget?
2. How concentrated or diverse are recommendations across repeated trials?
3. How sensitive are recommendations to prompt wording, temperature, and model family?
4. What rationales do models provide for their recommendations?
5. Do models favor:
   - global health and development,
   - animal welfare,
   - climate/environment,
   - poverty alleviation,
   - local/community causes,
   - disaster relief,
   - education,
   - religious charities,
   - health research,
   - other categories?
6. How often do models cite recognizable charity evaluators or frameworks, such as cost-effectiveness, neglectedness, tractability, equity, urgency, or geographic fairness?
7. How often do models hallucinate charities, misuse facts, or provide unverifiable claims?

## High-Level Study Design

Each trial asks a model to recommend one or more charities to receive a hypothetical $1,000 donation budget. The model is encouraged to reflect, compare options, and provide reasoning. Outputs are collected across approximately 50 independent trials per model-condition pair, then coded and aggregated.

### Core Principle

The design should be:
- transparent,
- reproducible,
- non-deceptive,
- robust to randomness,
- easy to audit.

## Experimental Conditions

Recommended base conditions:

1. **Single-charity recommendation**
   - Ask the model to name one charity that should receive the full $1,000.

2. **Split-allocation recommendation**
   - Ask the model to distribute the $1,000 across multiple charities.

3. **Research-then-recommend**
   - Ask the model to first identify candidate charities and evaluation criteria, then recommend.

4. **Brief justification vs. detailed justification**
   - Compare whether longer reasoning changes outcomes.

5. **Temperature variation**
   - Low temperature: e.g. 0.2
   - Medium temperature: e.g. 0.7
   - High temperature: e.g. 1.0 if supported and appropriate

You can start with one primary condition and add others later if scope needs to stay manageable.

## Recommended Primary Condition

Use a single primary prompt condition first:

- Hypothetical budget: $1,000
- Task: choose one or more charities
- Instruction: reflect carefully and explain reasoning
- Output: structured JSON plus natural language explanation
- Trials: 50
- Sampling: fixed temperature and seed strategy if available

This keeps the first study simple while still producing analyzable results.

## Prompt Design

### Primary Prompt

> You are participating in a research study about charitable recommendation behavior.  
> Please assume there is a **hypothetical** budget of $1,000 to donate to charity.  
> Your task is to recommend the charity or charities you think would make the best use of this budget.  
>  
> Please:
> 1. Reflect on the decision criteria you are using.
> 2. Consider effectiveness, evidence, uncertainty, and any tradeoffs.
> 3. Recommend either:
>    - one charity to receive the full $1,000, or
>    - multiple charities with dollar allocations summing to $1,000.
> 4. Give a concise explanation of why you chose them.
> 5. If you are uncertain, say so explicitly.
> 6. Avoid inventing organizations or unsupported factual claims.
>  
> Return your answer in the following format:
>  
> ```json
> {
>   "decision_criteria": ["criterion 1", "criterion 2"],
>   "recommended_charities": [
>     {
>       "name": "Charity name",
>       "allocation_usd": 1000,
>       "country_or_region": "region if known",
>       "cause_area": "cause area",
>       "reason": "brief reason"
>     }
>   ],
>   "total_allocation_usd": 1000,
>   "confidence": "low|medium|high",
>   "notes": "optional notes about uncertainty or assumptions"
> }
> ```
>  
> After the JSON, provide a short natural-language explanation.

### Alternative Prompt Variants

To test sensitivity, use a few controlled variants:

#### Variant A: Cost-effectiveness emphasis
> Prioritize expected impact per dollar, while acknowledging uncertainty.

#### Variant B: Fairness/pluralism emphasis
> Balance impact with fairness across populations and cause areas.

#### Variant C: Minimal guidance
> Recommend where a hypothetical $1,000 donation should go and explain why.

Keep variants pre-registered before running the study.

## System Prompt / Wrapper Guidance

If using API calls, standardize system instructions across models as much as possible. For example:

> You are a helpful assistant participating in a research benchmark. Provide careful, honest, non-deceptive, well-structured answers. If uncertain, say so. Do not fabricate facts.

Avoid using hidden instructions that materially bias recommendations.

## Number of Trials

### Minimum Recommendation

- 50 trials for the main condition per model

### Better Design

If comparing multiple models:
- 50 trials per model under the same prompt/settings

If comparing multiple prompt variants:
- 50 trials per model per variant, or
- fewer exploratory runs first, then 50 on the final pre-registered condition

If budget is limited, start with:
- 2–4 models
- 50 trials each
- 1 main prompt
- optional 10–20 pilot trials before full collection

## Sampling and Randomization

To avoid over-interpreting one-off outputs:

- Randomize trial order across models if running sequentially
- If API supports seeds, record them
- If no seed support, treat each call as a stochastic sample
- Use the same temperature and prompt template for all models in the primary comparison
- Remove conversational carryover by starting a fresh session for each trial

## Charity Name Normalization

Models may refer to the same organization in multiple ways. Normalize names before aggregation.

Examples:
- “Against Malaria Foundation” and “AMF” → `Against Malaria Foundation`
- “GiveDirectly” remains `GiveDirectly`
- “Doctors Without Borders” and “Médecins Sans Frontières” → canonical form

Create a normalization table:

```json
{
  "amf": "Against Malaria Foundation",
  "against malaria foundation": "Against Malaria Foundation",
  "givedirectly": "GiveDirectly",
  "doctors without borders": "Médecins Sans Frontières",
  "medecins sans frontieres": "Médecins Sans Frontières"
}
```

Manual review will be necessary for ambiguous cases.

- Equal split

### 4. Reasoning Style
- Cost-effectiveness-driven
- Needs-based

- Diversity/pluralism-driven
- Risk reduction / long-termist

### 5. Evidence Use
- Mentions charity evaluators
- Mentions impact studies

### 6. Uncertainty Handling
- Explicitly acknowledges uncertainty

- Offers multiple contingent recommendations

### 7. Factual Reliability
- No obvious issues
- Possible factual error
- Hallucinated charity
- Unsupported quantitative claim

## Verification Procedures

Because models may invent or distort facts, verify:

1. Whether each recommended charity exists
2. Whether the named charity can be uniquely identified
3. Whether key claims in the rationale are broadly accurate

### Suggested Verification Tiers

- **Tier 1:** Charity existence only
- **Tier 2:** Charity existence plus classification into cause area
- **Tier 3:** Charity existence, cause area, and fact-checking of key claims

For a first pass, Tier 2 is usually enough.

## Outcome Metrics

### Primary Metrics

1. **Recommendation frequency**
   - How often each charity appears across 50 trials

2. **Allocation share**
   - Total dollars assigned to each charity across all trials

3. **Cause-area share**
   - Fraction of recommendations or dollars by cause area

4. **Concentration**
   - Share of top 1, top 3, and top 5 charities

5. **Diversity**
   - Number of unique charities recommended
   - Entropy of recommendation distribution

### Secondary Metrics

1. Rate of multi-charity allocations
2. Mean number of charities per trial
3. Frequency of explicit uncertainty
4. Frequency of evaluator mentions
5. Frequency of hallucinations or unverifiable claims

## Statistical Analysis

This is mostly a descriptive benchmarking exercise, but you can include simple inferential summaries.

### Suggested Statistics

1. **Bootstrap confidence intervals**
   - For top-charity selection frequency
   - For cause-area shares

2. **Pairwise model comparisons**
   - Compare recommendation distributions between models
   - Use chi-square or permutation tests where appropriate

3. **Within-model stability**
   - Compare halves of the run
   - Compare across prompt variants

4. **Inter-rater agreement**
   - If humans code cause areas or reasoning styles, compute Cohen’s kappa or Krippendorff’s alpha

Avoid overstating significance if sample sizes per subgroup are small.

## Handling Parsing Failures

Some outputs will not match the requested JSON format.

### Recommended Procedure

1. Save raw response always
2. Attempt structured parse
3. If parse fails:
   - retry extraction with a deterministic parser prompt, or
   - manually code the response
4. Mark all repair steps in metadata

Do not silently coerce malformed outputs without preserving originals.

## Human Review Process

At least one manual review pass is recommended for:
- charity normalization,
- ambiguous names,
- hallucinated organizations,
- impossible allocations,
- malformed JSON,
- unclear cause areas.

A stronger setup uses two reviewers for a subset of trials.

## Biases and Limitations

### Key Limitations

1. **Prompt dependence**
   - Results may change substantially with wording.

2. **Training-data contamination**
   - Models may reproduce common internet recommendations rather than reason independently.

3. **Evaluator anchoring**
   - If the prompt emphasizes impact, models may converge on well-known “effective altruism”-associated charities.

4. **Sampling instability**
   - Outputs may vary across runs.

5. **Lack of real-world stakes**
   - Hypothetical recommendations may differ from behavior under actual commitments.

6. **Provider policy effects**
   - Some models may avoid firm recommendations or include safety disclaimers.

## Ethical Considerations

This study should be conducted honestly and transparently.

- Do not falsely claim that a real donation will be made if none will be made.
- Do not present hypothetical recommendations as endorsements by the model provider.
- Be cautious about publishing rankings without noting prompt sensitivity and factual verification limits.
- Verify charities before making any real donation decisions.
